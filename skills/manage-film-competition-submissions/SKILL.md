# 影视比赛投稿策略

围绕作品管理投稿生命周期，不把比赛当作互不相关的清单。先保护资格、版权和首映价值，再推荐真实可行的机会。

执行前完整读取 [研究与核实契约](references/research-contract.md) 和 [数据与输出契约](references/data-contract.md)。需要首次建立档案时使用 `assets/` 模板和 `scripts/competition_registry.py`，不要自行发明平行格式。

## 定位工作区

按以下顺序定位，不写死盘符：

1. 优先使用用户明确指定的工作流根、项目根或作品范围。
2. 从当前目录向上寻找 `00_开始这里.md`；找到后将其目录视为工作流根。
3. 否则读取 `$CODEX_HOME/xiaomo-ai-film-workflow.json`；未设置 `CODEX_HOME` 时读取用户目录 `.agents/xiaomo-ai-film-workflow.json`，使用其中的 `workflowRoot` 和 `projectsRoot`。
4. 仍无法定位时进入咨询模式：说明未读取本地项目，只给方法或基于用户所给材料的条件性分析，禁止写文件。

组合模式默认检查 `projectsRoot` 下直接包含 `开始这里.md` 与 A/B/C 和新旧 D 主文件的项目；项目真实存在 `E_发行复盘.md` 时才额外读取 E，不要求旧项目补建 E。用户指定作品时只缩小本次分析范围，持久数据仍集中保存在 `workflowRoot/投稿管理/`。

排除明确标记为测试、合成评测、fixture、sandbox 或非真实创作的目录。仅凭文件夹名称无法确定时保持排除并说明；用户明确要求纳入后才读取。

## 只读摸底

先读取既有 `投稿管理/参赛者档案.md`；不存在时把在校状态、年龄范围、所在地、团队条件、预算、出行、语言和跨境支付能力记为未知，不要默认为符合。

对每个真实项目最小读取：

1. `开始这里.md` 的项目身份。
2. A/B/C/D 主文件中与作品阶段、采用状态和最近交接直接相关的内容；若项目有 E，再从 E 读取公开发布、回执和发行状态。
3. 明确引用的剧本、分镜、资产、生成记录、成片、字幕、授权或发布记录。
4. 视频、图片和音频先读文件名、大小、格式、时长、分辨率等元数据；只有比赛条件确实需要时才检查内容。

不得上传、粘贴或向搜索服务发送未公开剧本、提示词、素材或成片。没有文件证据时标记未知，不根据作品名或目录结构猜测完成度。

若 `投稿管理/` 已存在，首次读取所有可能更新的文件时记录 SHA-256 快照。研究和报告阶段零写入。

## 执行流程

### 1. 建立资格基线

分别整理参赛者资格、作品阶段、可投稿形态、AI 使用、完成日期、公开与展映历史、版权材料、可用版本和首映状态。缺失关键身份或作品事实时，只给条件性结论，并把最关键问题列入待确认事项。

### 2. 联网发现机会

必须使用当次实际日期和网络工具，同时以中英文检索国内外机会。覆盖未来 `0–60` 天、`61–180` 天和年度重点机会。网络不可用时停止当前比赛事实核实，不用记忆补全。

聚合站、自媒体和往届列表只用于发现线索。正式核实回到本届官网、规则文件、报名页、官方账号或正式投稿平台。

### 3. 建立官方证据

逐场记录本届年份、官方链接、报名链接、核实日期、注册截止、作品截止、时区及北京时间。区分官方事实、代理推断和待确认项；规则冲突时指出页面、版本与冲突内容。

### 4. 先过硬性门

依次检查开放状态、报名入口、中国大陆资格、学生/年龄/团队条件、作品类别和完成时间、截止前可行性、AI 政策、授权证明、首映与公开限制、版权条款和实际成本。

硬性失败标为“不建议”。强制转让核心版权直接硬性失败；永久、免费、全球、不可撤销并允许商业修改或转授权的广泛许可默认“不建议”，比赛状态仍保持“候选”。只有用户明确接受该许可风险后才可重新评估，且最高为 B。关键资格未知、AI 政策未说明或官方信息冲突时，比赛状态仍用“候选”，另将核实结论记为“待核实”；不得进入正式优先榜。

### 5. 匹配作品并评分

只给通过硬性门的组合评分。每场比赛可以匹配多部作品，但必须分别说明推荐单元、缺失材料、修改项、准备工时、成本、资格可行性、置信度和对后续路线的影响。

不预测获奖概率。正式优先推荐控制在 3–10 个；不足时按真实数量输出，不凑数。

### 6. 检查路径冲突

对同一作品的候选比赛检查首映级别、网络公开、独家展映、参加其他比赛、自动公开、永久授权、商业使用、修改和转授权冲突。比较战略价值并给出投稿顺序、暂缓公开或放弃建议，不按截止日期机械排序。

### 7. 形成行动路线

按“作品完成前 → 第一轮高价值/首映敏感投稿 → 第二轮开放型投稿 → 公开发布”组织每部作品。每个推荐对应一个可执行动作、前置条件、负责人未定项和明确日期。

### 8. 输出报告

严格按数据契约的九个部分输出。所有当前比赛事实紧邻附官方来源链接和核实日期；国际截止注明原时区和北京时间。没有可信新增机会时原样写出：

> 本次未发现符合当前作品条件且值得优先参加的新增比赛。

## 采用后写入

只有用户明确采用本期结果或明确要求初始化/更新投稿档案后才写入：

1. 若目录不存在，先运行 `python -X utf8 scripts/competition_registry.py init --root <workflowRoot>/投稿管理 --dry-run` 展示将创建的内容；复核路径后去掉 `--dry-run`。
2. 写前重新运行 `snapshot`。与首次读取快照不一致时立即停止，报告并发变化，不覆盖。
3. 使用 `next-id --year YYYY` 为新比赛分配稳定 ID；同一比赛先按官方 URL、年份、名称和主办方去重。
4. 只增量更新 `投稿管理/`。不写现有项目、活动工作流、Skill 源码或知识工程，不删除历史条目，不回收 ID。
5. 运行 `validate`；验证失败时修复本次写入，不把无效状态宣布为完成。
6. 在变更日志中记录执行日期、核实范围、新增、规则变化、状态变化、采用依据和仍待确认项。

比赛状态只能使用：`候选、推荐、准备中、已提交、入围、获奖、未入围、已截止、已放弃、已归档`。`已核实/待核实` 属于独立的核实结论，不是比赛状态。

## 外部动作边界

- 只生成主办方问询邮件草稿；发送需要单独授权。
- 不注册投稿账号，不勾选授权协议，不报名，不付款，不上传作品，不公开作品。
- 用户授权某个外部动作时，只执行该动作，不把授权扩展到其他比赛或后续步骤。
- 不因奖金或证书高而忽略主办方可信度、版权和首映风险。

## 工具命令

从 Skill 根目录运行：

```powershell
python -X utf8 scripts/competition_registry.py init --root "<工作流根>/投稿管理" --dry-run
python -X utf8 scripts/competition_registry.py snapshot --root "<工作流根>/投稿管理"
python -X utf8 scripts/competition_registry.py next-id --root "<工作流根>/投稿管理" --year 2026
python -X utf8 scripts/competition_registry.py validate --root "<工作流根>/投稿管理"
```

脚本只管理本地结构和验证，不联网、不投稿。真实规则判断仍须读取官方来源。
