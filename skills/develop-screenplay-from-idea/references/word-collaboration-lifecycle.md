# Word 协作生命周期

## 目的与权威边界

本协议只解决 B 阶段中的可编辑 Word 往返、并行差量、采用源稿和生产绑定。故事创作状态仍使用本 Skill 的滚动确定协议，项目持久状态仍只有 `待定/采用/停用`；下文的版本角色和状态不是第四套创作状态。

B 阶段完成只按共享 [B_STAGE_READY v1](../../orchestrate-ai-film-project/references/b-story-stage-ready-contract.md) 判定。本协议提供 Word 工件、谱系、冲突、采用和释放证据，不自行宣布 `PASS`。

## 何时启用

Word 是按需协作界面，只在以下工作已经成为当前任务时启用：

- 正式对白及潜台词精修
- 场景动作和观众可见/可听的故事层场记
- 场次之间的人物、时间、空间、道具、信息和状态连续性
- 真实朗读或另获授权的 TTS 计时
- 最终文字、段落和版式精修

概念、一句话故事、前提、人物关系、故事系统、宏观结构和分场探索继续在对话中推进，并按既有门写 B。故事层场记只描述剧情理解所需的场景标题、出入场、动作结果和连续性，不代替 C 的场景制作卡、表演、镜头、灯光或提示词。

进入允许阶段也不自动授权创建、复制或修改文件。文件写入、B 记录写入、创作采用、制作释放、TTS 和下游媒体动作仍分别核对。

## 只以已保存文件为同步点

- Codex 能读取的只是磁盘上已经保存的 `.docx` 字节，不能声称看见 Word 窗口内尚未保存的修改。
- 用户可以持续编辑活动 Word，不需要关闭文档、交出唯一编辑权或手工维护分支。Codex 不直接改活动 Word，只操作从某个已保存同步点生成的快照、修订/批注副本或差量包。
- 每次读取、差量、合并、采用或释放前都绑定精确路径、版本和 SHA-256。文件名、Word 内部标题、修改时间、逐场对齐或名称中的“最终版”都不能替代 hash 和用户决定。
- 无法取得稳定保存快照、读取期间 hash 改变、来源路径/hash 与 B 指针不符时零写入停止。请用户保存后再取新快照；不得猜测未保存内容，也不得沿用旧基线覆盖当前文件。

## 六个版本角色

每个角色只在真实到达该节点时建立；不是每轮都机械生成六份文件。

| `role` | 含义 | 允许状态 | 关键约束 |
| --- | --- | --- | --- |
| `base` | 双方共同认可的已保存同步基线 | `saved` | 一轮用户/Codex 并行差量必须指向同一 `base` |
| `user` | 活动 Word 相对 `base` 的最新已保存快照 | `saved` | 只代表磁盘保存态，不代表采用 |
| `codex` | Codex 从 `base` 派生的修订、批注副本或可应用差量 | `under_review` | 不得以活动 Word 为输出路径 |
| `merged` | 用户与 Codex 的差量已无未决重叠后形成的新候选 | `merge_ready` | 只写新文件；必须有绑定共同 `base`、双方版本/hash、合并稿 hash 与空冲突集的项目内证据 |
| `adopted` | 用户明确创作采用的不可变源稿 | `adopted` | 采用证据与 B 写入证据分别记录；不得原地改 |
| `production` | 已有独立制作释放证据并绑定精确 `Sxx` 范围的生产版本 | `released` | 只能来自 `adopted`；非字节一致派生还必须证明正文、场次顺序、冲突与视觉 QA 均通过 |

每份版本记录至少包含：

```yaml
schema: screenplay-word-lineage-v1
version_id: 唯一版本 ID
role: base | user | codex | merged | adopted | production
status: saved | under_review | merge_ready | adopted | released
path: 精确 .docx 路径
sha256: 文件 SHA-256
parent_version_ids: []
captured_at: ISO-8601
scope_anchors: []
sxx_scope: null
write_authorization_evidence: 精确定位
adoption_evidence: null
production_release_evidence: null
conflict_manifest_path: null
merge_evidence_path: null
production_derivation_evidence_path: null
```

角色文件和元数据放在 B 已登记的项目内版本账目录，推荐位于 `剧本/历史/Word协同版本账/`，默认不进入启动读取集。B 只保存该目录、当前角色指针和 hash；完整谱系由后台元数据恢复，用户不需要看见或维护分支。

## 一轮并行协作

1. 用户明确保存后，以活动 Word 的磁盘版本建立不可覆盖的 `base`；若已有同 hash 的当前基线可复用。
2. 用户继续编辑活动 Word。Codex 只从 `base` 派生 `codex` 副本或差量包；两者互不锁死。
3. 准备汇合时重新读取活动 Word 的最新保存态，建立 `user`。若 hash 在读取或复制期间变化，放弃本次临时输出并重新取保存快照。
4. 计算 `base→user` 与 `base→codex` 的锚点差量。用户一侧没有变化时可以直接审查 `codex`；Codex 一侧没有变化时可以直接审查 `user`，不为形式完整机械制造 `merged`。
5. 冲突集为空时，把所有非重叠差量写入新的 `merged` 候选。输出前再次核对两个父版本 hash，并保存 `screenplay-word-merge-evidence/v1` JSON：精确记录共同 `base`、`user`、`codex` 的版本/hash、合并稿 hash、空 `unresolved_conflicts`、方法和证据定位；永不覆盖任何父版本或采用稿。版本账必须先验证该证据再登记 `merge_ready`。
6. 有冲突时只交冲突清单和可应用的非重叠差量，不建立 `merged`、不擅自选边。用户逐项选择后，从明确父版本重做新候选。
7. 用户明确采用精确版本后才建立 `adopted`。若还没有 B 写入授权，只报告采用决定和待落账状态，不修改 B。

## 锚点、差量与冲突

最小合并单元是稳定场次锚点下可可靠定位的段落或结构节点。优先使用 Word 书签/段落 ID；没有可靠内部 ID 时，组合使用场次稳定锚点、场景标题、前后文指纹和基线段落 hash。页码、行号和段落序号只能作提示，不能单独作为锚点。

以下情况视为重叠冲突：

- 双方修改同一锚点或同一段落的相交文本范围
- 一方删除，另一方修改、批注或移动同一对象
- 双方重排同一场次，或一次重排跨过另一方修改范围
- 正文不冲突，但样式、修订、批注、书签或场次边界无法可靠共同保留
- 工具无法把任一差量唯一映射回共同 `base`

冲突记录至少包含 `base/user/codex` 版本 ID、场次锚点、冲突类型、三方短摘录或差量摘要、受影响 `Sxx`、待用户决定项和“未写入目标文件”。不把多份全文复制进 B。

## 文档工具与降级

已获得 Word 写入授权且具备能保留 DOCX 结构的文档工具时：

1. 只打开 `base` 或其工作副本，输出到新的 `codex` 路径。
2. 能可靠保留修订和批注时使用修订/批注；工具不支持时不得伪造“已开启修订”。
3. 修改后重新计算 SHA-256，并 render 为逐页图像做视觉 QA；至少检查页数、场次顺序/锚点、缺字截断、段落样式、分页和用户点名版式。
4. render QA 通过只证明当前副本可审阅，不等于用户采用、B 已写入、制作已释放或外部动作获准。

没有合适文档工具，或工具无法安全保留修订、批注、书签和版式时，不直接修改 `.docx`。交付差量包，至少包含：共同 `base` 路径/版本/hash、目标场次锚点、基线短摘录、建议替换/插入/删除/批注、理由、预期影响和冲突项。差量包仍是候选，不得声称已写回 Word。

## 采用源稿、清洁稿与生产绑定

- `adopted` 是用户明确采用的源稿，建立后不可原地编辑、接受修订、清除批注、改样式或重排分页。后续修改必须从它派生新的 `base` 或工作副本。
- 清洁稿是可选派生物，只能在用户明确要求且已获文件写入授权时，从精确 `adopted` 生成。允许的清洁范围必须事先列明；默认不改变标准化正文、场次顺序和锚点，并执行正文一致性检查与 render QA。
- 用户指定“原文件就是最终版”时，记录 `清洁稿：不适用＋原因`，让 `production` 绑定该原文件或其字节完全一致的不可变快照。不得清理批注、接受修订、规范样式、调整段落或分页。
- `production` 只在同时存在用户创作采用、B 写入落账、独立制作释放证据和精确 `Sxx` 范围后建立。它可以与 `adopted` 指向相同路径/hash；角色变化不要求重复复制或修改文件。
- `production` 与 `adopted` 字节一致时直接登记 `byte_identical`，不需要派生证明。hash 不同时必须提供项目内 `screenplay-word-production-derivation/v1` JSON，精确绑定 adopted 版本/hash 与 production hash，并同时证明 `standardized_text_equal=true`、`scene_anchor_order_equal=true`、空 `unresolved_conflicts`、`visual_qa=passed`、方法和证据定位；缺一即不得登记 `released`。
- `visual_qa=passed` 必须指向真实 Word/渲染逐页检查证据。单元测试中的 passed 哨兵只验证代码分支，不能用于正式 production。运行环境没有 LibreOffice/`soffice` 时，结构检查不能冒充页面保真；应继续使用 byte-identical adopted，或由用户在 Microsoft Word 中完成可定位的人工视觉 QA 后再登记派生稿。

## 四类决定必须分开

1. **用户创作采用**：决定哪一精确 Word 版本及哪些场次内容成立。
2. **B 记录写入**：允许把采用决定、指针、hash、冲突、Sxx 映射和交接落入 `B_故事剧本.md`；创作采用本身不自动授权写入。
3. **进入制作释放**：明确哪些已采用场次现在进入制作。缺此证据时留在 B，不能建立 `production`、不能把 `B_STAGE_READY` 写为 `PASS`、不能交 A 派 C。
4. **外部动作授权**：Word 修订/批注、快照文件、TTS、图片/视频/声音生成、剪辑、封面、上传和发布分别按点名范围授权。采用、B 写入、制作释放、`Sxx` 和 `PASS` 均不替代这些授权。

同一条用户消息可以同时提供多类证据，但必须能分别定位其对象、范围与动作；模糊的“先看看”“对一下”或文件名不能补足任何门。

## B 主文件与阶段完成

B 的 Word 活跃区只保留：

- 活动 Word、最近 `base`、最新 `user/codex/merged` 候选、`adopted` 和 `production` 的精确路径/版本/SHA-256
- 当前协同状态、用户未同步内容为“不可见/未知”的声明、冲突数量与冲突清单指针
- 用户创作采用、Word/快照写入、B 写入和制作释放的精确证据定位
- 场次稳定锚点、正文 hash 与 `Sxx` 版本映射
- 清洁稿状态、历史策略、当前阻塞和最近交接

B 不保存多版 Word 全文、完整修订记录或全量冲突正文。旧工作稿与候选不自动删除，按项目历史策略保留，默认不读。

准备结束 B 阶段时读取共享 [B_STAGE_READY v1](../../orchestrate-ai-film-project/references/b-story-stage-ready-contract.md)。Word 工件存在、render QA 通过、逐场确认、采用或已分配 `Sxx` 都不能单独构成 `PASS`。

## 场次锚点、Sxx 与进入 C 后的变更

- Word 场次先有稳定锚点；用户明确采用并释放进入制作时，B 才把锚点映射到 `Sxx vNN`。一个整稿 hash 变化不能替代逐场影响分析。
- C 尚未启动时，同一事件结果和制作功能内的对白、动作、连续性或时长修订保留 `Sxx` 并升版；功能、事件结果或制作目的改变时停用旧 `Sxx` 并建立新编号。
- C 已启动后，B 只返回改变的锚点、旧→新 `Sxx` 版本、必须保持项和精确下游影响坐标。A 同步指针，C 仅把命中锚点的资产/场景卡/Vxx/Setup/take 标为待复核或失效；未命中的锚点和依赖继续有效。
- 触及已冻结/锁定下游、改变事件结果或制作功能、影响第二名所有者，按 A 的重大串行路由处理；不得把整份 Word hash 漂移机械传播成全剧失效。

## 确定性快照脚本

需要建立不可覆盖的已保存快照时，可调用 `scripts/screenplay_word_snapshot.ps1`。调用者必须显式提供源 `.docx`、版本账根目录、角色、版本 ID、父版本和文件写入授权证据；`merged` 必须用 `-MergeEvidencePath` 指向版本账根目录内的项目 JSON，且 `user/codex` 必须共享同一个精确 `base`；`adopted` 另需采用证据；`production` 另需制作释放证据与 `Sxx` 范围，源 hash 不同于 adopted 时还必须提供 `-ProductionDerivationEvidencePath`。

脚本只做稳定 hash、证据门验证、不可覆盖复制和元数据记录，不读取 Word 未保存内容，不执行差量/合并，不改活动 Word，不判断创作采用或 `B_STAGE_READY`。两类证据文件的路径、SHA-256 和 production 绑定类型写入元数据；证据只能位于当前项目的版本账根目录。`-DryRun` 执行全部父版本、hash、冲突与视觉 QA 检查，只返回计划且不创建目录或文件。

任何脚本成功只证明某个已保存磁盘版本已被安全快照，不证明 Word 内容正确、用户已采用、B 已落账、制作已释放或下游动作已授权。

## 停止并报告

遇到以下任一情况，保留现有不可变版本并零覆盖停止：

- 用户尚未保存，而任务依赖其最新修改
- 源文件在读取/复制期间改变或无法稳定读取
- 当前活动 Word、B 指针和预期 `base` 无法建立唯一三方关系
- 差量无法可靠定位、存在未决重叠冲突或文档工具不能保真
- 采用、B 写入、制作释放或点名外部动作中缺少本轮所需证据
- `adopted`/`production` 将被原地修改，或用户要求保留原文件却将发生清洁/重排版
- Sxx/锚点影响扩散到已冻结下游且尚未完成 A 路由

报告已确认的保存版本/hash、已经产生的候选或快照、未写入项、冲突和继续所需的一个最小动作；不得把冲突、差量包或快照写成已合并、已采用或已释放。
